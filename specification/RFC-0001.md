# RFC-0001 — ORBIT: Polyglot Orchestration Language

| | |
|---|---|
| RFC | ORBIT-0001 |
| Version | 0.1.0 |
| Status | Accepted baseline, implemented in this repository (see [Appendix A](#appendix-a--v010-implementation-record)) |
| Paradigm | Declarative DSL |
| Compiler / runtime | Rust |
| Execution model | Independent runtime, single-node first |
| Worker protocol | Protocol Buffers schema; HTTP/JSON and gRPC bindings |
| Storage | SQLite or PostgreSQL |
| Source extension | `.orbit` |
| IR version | `orbit-ir/1` |

> One workflow. Every language. Reliable execution.

## 1. Abstract

ORBIT is a specialized declarative programming language for defining,
compiling, executing and managing workflows across heterogeneous software
systems. It coordinates applications written in Python, TypeScript, JavaScript,
Go, Rust, Java, C# and other languages without rewriting their business logic.

ORBIT consists of a language, a compiler, a typed intermediate representation,
an execution runtime, a worker communication protocol and developer tooling.
It is responsible for expressing distributed workflows, defining execution
dependencies, managing workflow state, handling retries and timeouts,
coordinating heterogeneous workers, providing durable execution, recovering
from failures, running compensating actions, validating service contracts, and
providing unified execution observability.

ORBIT does not replace general-purpose languages. It is a specialized layer for
coordinating programs written in them.

## 2. Design philosophy

1. **Language independence.** Workflow definitions do not depend on the
   implementation language of the workers that take part.
2. **Durable execution.** Workflow progress survives runtime restarts and is
   recovered from persisted history.
3. **Explicit semantics.** Retries, timeouts, dependencies, concurrency,
   compensation and error handling have well-defined semantics.
4. **Developer productivity.** The language is readable, concise and easy to
   debug.
5. **Contract safety.** The compiler detects incompatible inputs, outputs and
   dependencies before execution whenever possible.
6. **Incremental adoption.** Existing applications take part through SDKs,
   network protocols and adapters.

## 3. Scope

### 3.1 Included in v0.1

The dedicated language; lexer and parser; AST; semantic analysis; static type
checking; typed IR; dependency analysis; single-node engine; durable history;
worker registration; Python SDK; TypeScript SDK; worker protocol; HTTP
integration adapter; retries and timeouts; basic compensation; execution CLI;
structured logs.

### 3.2 Excluded from v0.1

Multi-node scheduling; HA clusters; worker federation; distributed consensus;
automatic exactly-once external execution; marketplace; simulation; GPU
scheduling; self-hosting compiler; production visual editor.

## 4. Language overview

A **workflow** is the primary executable unit. Steps call **workers** through
typed **task contracts**:

```orbit
import "contracts.orbit"

workflow OrderProcessing {
    version "1.0.0"
    input  { order_id: String, customer_id: String, amount: Float, items: List<LineItem> }
    output { status: String, transaction_id: String? }

    step validate_order {
        worker "orders.validate"
        using typescript
        with { order_id: input.order_id, amount: input.amount, items: input.items }
        timeout 10s
    }
    step analyze_risk {
        worker "risk.analyze"
        using python
        after validate_order
        with { customer_id: input.customer_id, amount: input.amount }
        retry { attempts: 3, backoff: exponential, initial_delay: 1s, max_delay: 30s }
    }
    step process_payment {
        worker "payments.charge"
        using python
        when analyze_risk.score < 0.8
        with { order_id: input.order_id, amount: input.amount, currency: "USD" }
        idempotency_key: input.order_id
        compensate {
            worker "payments.refund"
            with { transaction_id: process_payment.transaction_id, amount: input.amount }
        }
    }
    return { status: "completed", transaction_id: process_payment.transaction_id }
}
```

The full reference example is [`examples/order_processing.orbit`](../examples/order_processing.orbit).
The language guide is [the language guide](../docs/src/language/workflows.md).

## 5. Grammar

The normative grammar is [`grammar.ebnf`](grammar.ebnf). Highlights:

* Tokens: identifiers `[A-Za-z_][A-Za-z0-9_]*`, double-quoted single-line
  strings with escapes, 64-bit integers, floats, booleans, `null`, duration
  literals (`500ms 30s 5m 2h 1d`), operators and punctuation.
* Comments: `//` and nestable `/* */`.
* Keywords are contextual; only `true`, `false` and `null` are reserved.
* Declarations: `workflow`, `schema`, `task`, `import`.
* Workflow members: `version`, `description`, `timeout`, `input`, `output`,
  `step`, `return`. `on event` / `on failure` are reserved (§A.3).
* Step members: `worker` | `sleep`, `using`, `after`, `with`, `timeout`,
  `queue_timeout`, `retry`, `idempotency_key`, `when`, `compensate`.
* Expressions with precedence `||` < `&&` < `== !=` < `< <= > >=` < `+ -` <
  `* / %` < unary `! -` < postfix `.field [index]`, plus `if … then … else`
  and built-in calls.

## 6. Type system

Static, schema-aware and structural. Its main job is to find invalid workflow
contracts before execution.

* Primitives: `String`, `Int` (i64), `Float` (f64), `Bool`, `Bytes`,
  `Duration`, `Timestamp`, `UUID`, `JSON`.
* Composites: `List<T>`, `Map<String, T>`, `T?`, named schemas, anonymous
  records.
* Workflows declare input and output schemas. Every worker contract (`task`)
  declares input and output.
* The compiler validates workflow inputs, worker input and output
  compatibility, references to step outputs, return type compatibility,
  optional values, dependency references and missing required fields.

Future: generics, unions, enums, result types, ADTs, schema compatibility
rules, refinement types, effect analysis.

## 7. Typed intermediate representation

The compiler lowers source to `orbit-ir/1` JSON. The IR does not depend on
source formatting or on worker languages, and it is the contract between the
compiler and the runtime. It holds workflow identity and version, a
`definition_hash`, resolved input and output types, steps in deterministic
topological order (id, action, sorted dependencies, typed input expression,
condition, idempotency key, timeouts, retry policy, compensation, output type),
the result mapping, every referenced task contract, and a source map.

### 7.3 Invariants (enforced by `WorkflowIr::validate`, by compiler and runtime)

* Step ids are unique, and every dependency names an existing step.
* The graph is acyclic (steps are stored in topological order).
* Every expression reads only the step's ancestors.
* Every task reference resolves to a contract with a matching version.
* Retry attempts are ≥ 1.
* `definition_hash` matches the content.
* Unsupported IR versions are rejected explicitly. The runtime never
  reinterprets them silently.

## 8. Worker protocol

Defined in [`protocol/orbit/worker/v1/worker.proto`](../protocol/orbit/worker/v1/worker.proto)
and documented in [`protocol/README.md`](../protocol/README.md).

A worker registers its identity, runtime and contracts, receives tasks, runs
business logic, returns results or structured errors, and reports health. A
worker never owns authoritative workflow state.

Operations: `RegisterWorker`, `Heartbeat` (carries cancellations), `PollTask`,
`CompleteTask`, `FailTask`, `UnregisterWorker`.

SDKs expose worker registration, task registration, typed input and output,
execution, error propagation, cancellation and health reporting. Python
(`sdks/python`), TypeScript (`sdks/typescript`), Go (`sdks/go`) and Rust
(`crates/orbit-worker`) are implemented. `examples/polyglot.orbit` runs one
workflow across all four.

## 9. Execution semantics

Normative details are in [the runtime documentation](../docs/src/runtime/executions.md). In short:

* **Workflow lifecycle:** `RUNNING → COMPLETED`, or `RUNNING → COMPENSATING →
  FAILED | CANCELLED | TIMED_OUT`, with a recorded compensation outcome.
* **Step lifecycle:** `PENDING → SCHEDULED → DISPATCHED → SUCCEEDED`, with
  `RETRY_WAIT`, `SKIPPED`, `FAILED`, `CANCELLED` and `WAITING`.
* **Eligibility:** every dependency succeeded or was skipped, the condition is
  true, and the workflow is not aborting. Independent steps run concurrently.
* **Retries:** fixed or exponential, always bounded. `attempts` counts every
  attempt, including the first.
* **Timeouts:** queue wait (`queue_timeout`), worker execution (`timeout`),
  and the whole workflow (`timeout` at workflow level). Cancellation is
  cooperative.
* **Idempotency:** every task carries a stable idempotency key. Delivery is
  at-least-once, and exactly-once external execution is not promised.
* **Compensation:** explicit business actions run in reverse completion order
  after failure, cancellation or timeout. It is not a database rollback.
* **Durable history:** every transition is an event, appended transactionally
  with the projection update. History is authoritative.
* **Crash recovery:** reload active executions, replay history, re-index
  in-flight work, resume. Uncertain outcomes are treated as *possibly
  completed*: they are redelivered with the same idempotency key, and late
  results are reconciled.
* **Fan-out:** a `for` step expands into one unit per list element, at most
  `max_parallel` at a time. Its output is the ordered list of results, and each
  succeeded element is compensated individually.
* **Child workflows:** a `workflow` step starts a durable child execution with
  a deterministic id. Results and cancellation flow between parent and child
  through continuous reconciliation.

## 10. Runtime architecture

One independent process (`orbit server`), modular inside: compiler (offline,
in the CLI), decider and scheduler, worker registry, execution engine,
persistence, recovery, observability. See `crates/orbit-runtime`.

Persistence uses the tables `workflow_definitions`, `workflow_executions`
(projection), `execution_events` (authoritative) and `worker_registry`, on
SQLite or PostgreSQL with identical semantics. Step, attempt and retry state is
derived from events rather than stored in competing tables (§A.2).
Observability: structured logs, Prometheus metrics, and OpenTelemetry traces
over OTLP/HTTP.

## 11. CLI and runtime API

CLI: `orbit init | check | validate | compile | fmt | graph | server | deploy |
run | status | inspect | logs | cancel | ps | workers list | token | lsp`.

API (`orbit-api/1`): `POST/GET /v1/workflows`, `POST/GET /v1/executions`,
`GET /v1/executions/{id}`, `/history`, `/wait`, `POST /cancel`,
`GET /v1/workers`, `GET /v1/health`, `GET /v1/metrics`. Errors are structured
(`{"error": {"code", "message"}}`). Authentication is required whenever the
API is exposed beyond loopback.

## 12. Compiler implementation

Stages: source loading (with imports) → lexing → parsing (with error recovery)
→ symbol resolution → type checking → dependency graph and cycle detection →
validation → IR generation → hashing and serialization. Diagnostics carry a
stable code, file, line, column, a source snippet, labels, notes and
suggestions. The catalog is [`docs/src/reference/diagnostics.md`](../docs/src/reference/diagnostics.md).

## 13. Security

Implemented in v0.1: authenticated runtime API (bearer token, constant-time
comparison); a restricted shared worker credential; per-worker identities (a
token hash or a client certificate name, allowed task patterns, and a runtime),
each confined to its own id, sessions and task tokens; HTTPS and mutual TLS
served in-process (rustls) on both HTTP and gRPC, with private-CA and
client-certificate support in every client; TLS to PostgreSQL; refusal to bind beyond loopback without auth; strict payload
validation; body size limits; no shell execution; an opt-in HTTP adapter
restricted to http(s); secret redaction in CLI output; workers are not trusted
just because they registered (results are validated, stale tokens are
ignored).

Planned: capability-based permissions beyond task patterns, resource limits
per execution, stronger worker isolation.

## 14. Performance and reliability goals

Initial targets (to be measured on documented hardware): dispatch overhead
< 10 ms p95, state lookup < 5 ms p95, 1,000 concurrent active executions, 100%
recovery correctness in fault-injection tests, zero lost committed events.
Durability must never be weakened silently to gain performance.

Observed in the e2e suite: a two-step polyglot workflow (Python → TypeScript)
completes in about 17 ms end to end on a development container.

## 16. Roadmap

1. **Language foundation**: done.
2. **IR**: done.
3. **Runtime foundation**: done (single node; SQLite or PostgreSQL).
4. **Interoperability**: done. HTTP/JSON and gRPC bindings; Python,
   TypeScript, Go, Rust, Java and C# SDKs.
5. **Reliability**: done. Retries, timeouts, idempotency, compensation,
   recovery, fan-out and child workflows. Next: a fault-injection harness for
   database failures.
6. **Developer experience**: done. CLI, `orbit fmt`, language server and VS Code
   extension, OpenTelemetry. Next: `orbit test`, `orbit replay`, `orbit simulate`.
7. **Distribution**: next. Multiple runtime nodes sharing PostgreSQL, worker
   federation, HA.

## 17. Versioning and compatibility

Three versioned surfaces: the language specification, the IR
(`orbit-ir/1`), and worker contracts. A workflow definition is immutable per
`name@version`. Running executions stay on their definition hash. Contract
compatibility is checked independently: workers receive only tasks whose
`name@version` they announced.

## 18–19. Vision and non-goals

ORBIT aims to make distributed application coordination a first-class
programming discipline: clusters, simulation, a visual debugger, static
analysis, profiling, a contract registry, migration tooling.

It does not aim to replace general-purpose languages, databases or message
brokers, to convert applications automatically, to guarantee exactly-once
external execution, or to be a visual-only builder.

## Appendix A — v0.1.0 implementation record

The changes and additions made while implementing this RFC. Each one is
reflected in the grammar, the docs and the tests.

### A.1 Language additions

| Addition | Why |
|---|---|
| `task "name" { version, input, output }` declarations | §6.3 requires worker contracts at compile time; they need a syntax. |
| `with <expr>` step member | The baseline grammar had no way to pass input to a worker. |
| Implicit dependencies from data references | `with { x: risk.score }` implies `after risk`, so the graph cannot drift from the data flow. |
| Conditional steps produce optional outputs | Skipped steps yield `null`, which the type checker enforces (`coalesce`). |
| Null-propagating member access | `a.b` is `null` when `a` is `null`, matching optional typing. |
| `sleep <duration>` steps | Durable timers, a core orchestration primitive. |
| `queue_timeout` | §9.5 distinguishes queue waiting from execution time. |
| `retry { non_retryable: [...] }` | Business errors (e.g. `CARD_DECLINED`) should never be retried. |
| `if … then … else`, indexing, built-in functions | Common mapping logic without a worker. |
| Contextual keywords | Lets `input`, `version`, `status` be ordinary field names. |
| `import "file.orbit"` | Implemented now (relative paths, deduplicated). |
| Field defaults (`= value`) in schemas and inputs | Applied by the runtime, carried in the IR. |
| `description` on workflows and tasks | Shown in tooling. |
| `for item in <list>` with `max_parallel` | Fan-out is the most common orchestration shape after sequencing. |
| `workflow "Name"` steps | Composition: reuse workflows as typed, durable building blocks. |
| `on event` / `on failure` | **Reserved**: parsed and rejected with E0105 until their semantics are specified. |
| Workflow `version` is mandatory | §17 immutability depends on it. |

### A.2 Runtime decisions

| Decision | Rationale |
|---|---|
| **Pull-based workers** (long-poll) | Workers need no inbound ports, work behind NAT, and get backpressure for free. Fits "workers are independent". |
| **HTTP/JSON binding first**, `.proto` canonical | Zero-dependency SDKs in any language. gRPC is a second binding of the same messages. |
| **SQLite** (WAL, `synchronous=FULL`) by default, **PostgreSQL** by URL | One schema, one set of guarantees. PostgreSQL statements run on a dedicated connection thread, because the `postgres` crate cannot run inside the server's async runtime. TLS follows `sslmode`, but certificates are always verified (stricter than libpq's `prefer`). |
| gRPC from the canonical `.proto` via `protox` | No system `protoc` needed to build. One `identify()` function enforces identical authentication on both bindings. |
| Per-worker identities in a TOML file, tokens stored as SHA-256 hashes | Least privilege for worker hosts; no plaintext secrets at rest. Client certificates map to identities by DNS SAN or CN. |
| `for` units keyed `step[i]`; `StepFanOut` records the evaluated list | The list is evaluated once and replayed from history, so the fan-out is deterministic across restarts. |
| Child executions with deterministic ids (`<parent>.<unit>`), continuous reconciliation | Starting a child is idempotent, and no parent/child state is lost on a crash. |
| OpenTelemetry via a small OTLP/HTTP JSON exporter with deterministic ids | Stable wire format, no heavy dependency tree, and no duplicate spans after restarts. |
| `orbit fmt` is a token-stream normaliser with a re-lex safety check | It cannot change meaning or drop comments; the check refuses to write if it would. |
| **Event-sourced state + pure decider** | Makes "history is authoritative" structural rather than a convention. The decider is deterministic and unit-tested with a fake clock. |
| Step/attempt/retry tables derived from events | Avoids competing state stores (§10.2). |
| Same-attempt redelivery for uncertain outcomes | Does not burn retry budget for runtime or worker crashes. |
| Reconciliation: accept results from any token of an unresolved step | Implements "uncertain outcomes are potentially completed". |
| Compensation waits for in-flight steps, then runs sequentially, newest first | In-flight steps may still succeed and then need compensating. |
| `COMPENSATED` recorded as an outcome (`compensation: completed`) instead of a separate state | The terminal status keeps the cause (failed / cancelled / timed out). |
| Idempotent execution start via client-supplied `execution_id` | Callers can retry `start` safely. |
| `definition_hash` (SHA-256, excludes source map) | Enforces immutability. Reformatting source does not change identity. |
| Output validation of worker results | Contract safety at runtime as well as compile time. |
| Built-in tasks namespace `orbit.*` | Hosts the HTTP adapter, disabled by default. |
| Six crates instead of fourteen | `orbit-syntax`, `orbit-ir`, `orbit-compiler`, `orbit-runtime`, `orbit-worker` (Rust SDK) and the CLI, published as `orbit-lang`. Modules mirror the RFC's components, and they can be split later without API changes. |

### A.3 Added in v0.2

- Typed signals and queries declared in the language (`signal`, `await`,
  `query`), with runtime endpoints, CLI commands and SDK client methods.
- `compute` steps and lambdas (`map`, `filter`, `find`, `any`, `all`) for
  deterministic transformations without a worker. Filtering a list before a
  `for` step is done with `filter` in a `compute` step.
- Static safety analysis (`compensated_by`, W0601–W0606, `--strict`) and
  `orbit compat` for safe evolution.
- `orbit-ir/2`, emitted only for workflows that use these features.

### A.4 Known gaps

Multi-node execution and HA; `on event` / `on failure` handlers; `orbit test`,
`orbit replay`, `orbit simulate`; per-execution resource limits and
capability-based permissions; published performance benchmarks.
